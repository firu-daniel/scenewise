# Task plan review — iteration 0

## Must Fix
1. **`task_1_plan.md` — the containment check runs on the requested prefix, but artifacts are written under `{prefix}/{job_id}`. A prefix one level above the state directory plus a job id equal to the state directory's basename still writes into the state prefix.**
   Task 1 compares only the normalised `job.artifacts_prefix` with the state prefix (Work bullet 2, step (c)). It then returns `job_prefix(job.artifacts_prefix.rstrip("/"), job.id)` without checking it (Work bullet 3). Take state prefix `file:///srv/state` and the request `uri_prefix = file:///srv` (or `file:///srv/artifacts/..`) with `job_id = "state"`. `JOB_ID_PATTERN` `^[A-Za-z0-9._:-]{1,200}$` allows `state`, and `job_id` refuses only `.` and `..` (`src/scenewise/domain/jobs.py` `job_id`).
   - The normalised prefix `/srv` is not equal to or under `/srv/state`, so (c) accepts it.
   - `artifacts_prefix` returns `file:///srv/state`, and `publish` writes `file:///srv/state/a1/audio.wav` and `…/a1/result.json`.
   - `LocalBlobStore._path` allows both writes, because the state directory is one of the output store's roots (`src/scenewise/service/bootstrap.py` `_stores`).
   - Task 2's fence also lets them through, because the spelt path `/srv/state/a1/…` is inside the fence's spelling.
   - The files land in `state/a1/`, which is job `a1`'s record folder. That is the attack the prompt describes ("They can create files inside another job's state folder"). It contradicts the story's own goal ("must never land artifacts under the state prefix") and the prompt's "No file is written anywhere under the state prefix for that job".
   - The default state prefix is `{cwd}/.scenewise/state` (`src/scenewise/service/config.py` `_default_state_prefix`), so `job_id = "state"` with `uri_prefix = file://{cwd}/.scenewise` reaches this even with no `artifact_roots` configured.
   - The context's conclusion that `job_prefix` is safe because "a job id is always exactly one safe segment" misses this. The danger is that one segment, added to an ancestor of the state directory, lands exactly on it.
   **Fix:** In `task_1_plan.md`, run step (c) on the folder the artifacts actually go to. Normalise `job_prefix(requested.rstrip("/"), job.id)` (the requested prefix with the job id appended) through `_location`, and refuse with `uri_not_allowed` when it equals the state location or lies under it. Alternatively, refuse when either the requested prefix or the appended folder is at or under the state location. Name this case in the Goal and in the `artifacts_prefix` docstring bullet. Add it to the Verification "Refused" list: `file:///srv` with job id `state` against `file:///srv/state`. Update the `job_prefix` / `record_uri` paragraph so it no longer suggests that one safe segment rules out every composition.

2. **`task_4_plan.md` — no unit row covers a prefix that becomes the state prefix once the job id is appended.**
   Task 4's tables hold job id `j` constant (`_job_with` builds `job_id("j")`). So nothing in the unit tier pins the case in finding 1, and the 100%-branch bar for `app` would not catch a regression there. The interface Task 4 restates from Task 1 (the "Depends on" bullets) also describes the check only on the requested prefix.
   **Fix:** In `task_4_plan.md`:
   - Let `_job_with` take a job id: `_job_with(prefix: str | None, job: str = "j")`.
   - Add refused rows `(STATE, "file:///srv", "state")` and `(STATE, "file:///srv/artifacts/..", "state")`. Optionally add `(BUCKET_STATE, "mem://bucket", "state")`.
   - Keep an accepted row showing that the same prefix with another job id is not refused if Task 1 allows that, for example `(STATE, "file:///srv", "other")`. Otherwise state that it is refused.
   - Update the restated Task 1 contract so it says the check also covers `{prefix}/{job_id}`.

3. **`task_6_plan.md` — the end-to-end test does not exercise the "parent prefix plus basename job id" spelling, and its "nothing under the state prefix" assertion keys only on the name `attacker`.**
   Task 6 is the prompt's required proof that "no file is written anywhere under the state prefix for that job". Its new assertion collects only paths whose parts contain `"attacker"`. A job whose id is the state directory's basename writes `state/a1/audio.wav` and `state/a1/result.json`, which contain no `attacker` part, so the assertion as planned cannot catch that write even if a row for it were added.
   **Fix:** In `task_6_plan.md`, add a test (or a parametrized case) that posts `_job("state", (inputs / "tone.m4a").as_uri(), victim.parent.as_uri())`. The `victim` fixture's state directory is `tmp_path / "state"`. Assert that it ends `failed` / `uri_not_allowed` and that `victim / "a1"` does not exist. More generally, snapshot `set(victim.rglob("*"))` before the post and assert that the only new paths are the posting job's own record files (`{job}/status.json`, `{job}/.status.json.meta.json`, `{job}/.status.json.lock` and the `{job}` folder). Do not filter on the literal `attacker`. State in the Verification bullet that this case fails against the pre-branch code.
